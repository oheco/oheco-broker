# C management SDK: safety and ownership

The standalone source API is [ob_api.h](../sdk/c/remote/ob_api.h) and [ob_api.c](../sdk/c/remote/ob_api.c). It has no Go runtime callback or automatic credential persistence. Build it from the source SDK with `sh sdk/c/build.sh`; fixed dependencies and runtime requirements are documented in [native dependencies](NATIVE-DEPENDENCIES.md).

## Security and ownership contract

- `ob_api_client_create` copies its immutable options. One client supports simultaneous requests; each request has a separate curl easy handle. Wait for all requests before destroying the client. Curl global initialization uses `pthread_once`; the SDK deliberately never calls process-global cleanup, avoiding racing other clients/peer code. The embedding application must not call `curl_global_cleanup` while any curl user is alive.
- Only HTTPS origins are accepted for remote hosts. TLS peer chain and hostname verification are **always enabled**, with a TLS 1.2 minimum. `ca_file` is optional: without it curl requests the BoringSSL default trust paths; on devices without a usable trust bundle HTTPS fails closed. Supply a PEM CA bundle for a private control server. There is no insecure verification switch and no included CA snapshot.
- Plain HTTP is accepted only for IPv4 `127.0.0.0/8`, IPv6 `::1`, or `localhost`. HTTP `localhost` is pinned to `127.0.0.1`, not resolved through DNS. Mapped IPv6, LAN hosts, credentials in URLs, non-root base paths, queries, and fragments are rejected. Plain HTTP is for local tests, not remote deployment.
- HTTP GET/POST/PATCH/DELETE are supported. API paths must start `/v1/`; origin changes, traversal, percent escapes, fragments, control characters, and unsafe query characters are rejected. Typed IDs are 1–128 ASCII alphanumeric/underscore/hyphen characters, serialized JSON values are escaped by cJSON, and bearer values cannot inject headers.
- Redirects, netrc, environment proxy settings, cookies, and verbose logging are not enabled. An SDK-owned `CURLOPT_SSL_CTX_FUNCTION` clears `SSL_CTX_set_keylog_callback` on each private BoringSSL context, after curl installs its callback and **before** curl creates the SSL object or begins a handshake. Therefore ambient `SSLKEYLOGFILE` does not log **SDK-request traffic secrets**, for TLS 1.2 or TLS 1.3, including concurrent requests. **Refined guarantee:** pristine curl can read that variable and open/create its target file during process-global initialization; the SDK cannot promise no file touch. A new file remains empty and an existing file gains no SDK-secret bytes. The SDK neither unsets nor changes the environment, deletes caller files, nor claims to suppress logging on unrelated caller-owned curl/TLS handles. Stock curl 8.22.0 has no documented TLS-keylog-disable build switch. A bearer is never forwarded to another origin. The SDK makes direct requests to its configured origin.
- Default request timeout is 15 seconds, including response transfer; a client accepts 1–300000 ms. Connect timeout is at most 5 seconds. A low-speed guard aborts stalled transfers. Requests are bounded to 256 KiB, response bodies to 1 MiB, and cumulative response headers to 64 KiB, including chunked responses. Empty successful responses return an owned empty string.
- JSON is validated before returning it. Known password-hash field names (`password_hash`, `passwordHash`, `hashed_password`) anywhere in a response are rejected. The control server itself must serialize only safe public tenant fields. The SDK emits **no logs**; diagnostics are fixed redacted messages, and carry only error code, HTTP status, and numeric curl transport code. It does not copy arbitrary server messages into diagnostics.
- On both successful and HTTP-error responses, a non-NULL `char *` belongs to the caller and must be released with `ob_api_response_free`; on transport/validation/limit errors it is NULL. Output variables are reset at call entry, so free the old response before reusing an output variable. Response buffers, credential structs, bearer copies, and SDK-created JSON strings are wiped when released. cJSON allocator hooks and locale must not change after threads start. The shared SDK-owned [JSON adapter](<../sdk/c/remote/ob_json.c>) serializes management and native-control parsing against pristine cJSON's process-global error-location state; callers sharing this cJSON instance must use the same adapter or otherwise coordinate parsing.

## Native persistent signaling

The exact wire protocol is [ob-signaling-v1](<WS-SIGNALING.md>). HTTPS origins map to WSS and validated loopback HTTP origins to WS. Authorization is an HTTP header, never a URL parameter. The private transport borrows immutable client configuration, creates one private curl easy handle per broker watcher/per session setup worker, and uses public `CURLOPT_CONNECT_ONLY=2`, `CURLINFO_ACTIVESOCKET`, `curl_ws_recv` and `curl_ws_send`. Every curl operation and cleanup stays on that control owner thread. The QUIC/data owner never calls curl or joins control work in order to revoke forwarding.

Text messages are reassembled across both partial frame reads (`offset`/`bytesleft`) and RFC6455 fragments (`CURLWS_CONT` marks every non-final fragment). Binary, invalid UTF-8/JSON, duplicate/unknown top-level keys, unsafe integer IDs, oversized messages and missing subprotocol fail closed. The shared [JSON adapter](<../sdk/c/remote/ob_json.c>) also checks original top-level unsigned decimal token spelling for wire version/ID/status/sequence and envelope version/sequence: tiny fractions rounded to integer doubles, decimal points, exponents, signs and overflow cannot pass schema checks. Valid business-body floats and opaque strings remain untouched; escaped ASCII key names retain ordinary JSON equivalence. General business-body parsing retains pristine cJSON semantics (including its bounded non-RFC numeric-spelling permissiveness); this change is strict about security-sensitive wire/envelope schema integers, not a wholesale RFC-8259 body-parser replacement. Each application frame/complete message is limited to 262144 bytes; each connection queues at most 64 frames and 1 MiB of original frame bytes, with at most eight in-flight RPC IDs. RPC results are correlated without losing queued capabilities/mailbox pushes. Automatic curl PONG behavior remains enabled. Partial sends and `CURLE_AGAIN` wait on the actual socket with cancellation/budgets.

The broker consumes initial/change session snapshots instead of GET polling; a session consumes initial/approval capabilities and durable opposite-side message pushes. Heartbeat, send, approve, TURN, delete and offline use WS RPCs, with `body:null` for no-body operations. There is no silent HTTP polling fallback. Reconnect preserves scope/cursor, with bounded exponential backoff and jitter; durable sends retain identical sequence/data across lost receipts. ACK follows actual semantic envelope/MAC validation and cursor consumption, not raw receipt. A lost non-idempotent TURN outcome fails setup rather than repeatedly minting credentials. A stopped peer cannot resurrect from a later lease reply. Heartbeats run through PAKE/ICE waits and remain active after ready; WS PING/PONG alone never grants a lease.

WS connect attempts are cancellable and capped at 1500 ms and the remaining authorization/setup deadline; foreground RPCs retain the configured API timeout, but native I/O enforces the last successful lease independently. Explicit lifecycle close makes a bounded best-effort WS RPC (300 ms total). If that fails or times out, the owner disconnects the now-unusable socket; one bounded idempotent REST cleanup request (300 ms) may then remain, just as when no socket existed initially. These are not continuous management polls. Netrc/cookies are compiled out of the pinned dependency profile; setting the compiled-out `CURLOPT_NETRC` returns `CURLE_UNKNOWN_OPTION` in stock curl and is intentionally unnecessary. The SDK still explicitly disables ambient proxies, redirects and verbose logging, and uses the same verified-CA/hostname/private-SSL-context policy for WSS as HTTPS.

## Tenant and device operations

Named wrappers cover automatic registration/login/logout, account retrieval/name/email changes/password changes, capabilities/usage, broker registration/list/get/rename/delete/usage/device-token rotation, device heartbeat/offline/session list, session creation/status/capabilities/heartbeat/delete/messages/approval/TURN. See the public header for the exact signatures and token scopes. A NULL explicit bearer means fallback to the client's tenant token; an empty explicit bearer means no authentication (used for registration/login). Explicit device/session tokens take precedence.

Registration uses BoringSSL `RAND_bytes` to create a UUIDv4 `tenant-UUID` name and a **32 lowercase hex** password (128 CSPRNG bits). This strengthens the original 16-hex password. Automatic registration fills `ob_api_credentials` **before** its HTTP POST and retains the generated credentials even if the request fails: the server may have committed the account before its response was lost. The caller can attempt login with those retained credentials to recover. The SDK never automatically retries non-idempotent registration. For crash-safe caller-managed storage, call `ob_api_credentials_generate`, persist the generated secrets yourself on a private filesystem if wanted, and call `ob_api_tenant_register_credentials` with exactly those values; the API itself never writes them to disk. A successful receipt is safe `{tenant,token}` JSON. The caller must call `ob_api_credentials_clear` when finished. There is no automatic credential persistence; any Go CLI XDG storage is separate from this C API.

Login and account mutations return tokens in response JSON; they never silently mutate an existing client. Construct another client with the new tenant token when required. Password changes invalidate prior tenant/device/session tokens according to the control API. **The native broker/peer password is never an HTTP field**: peer authentication material is produced by the native PAKE engine and only opaque signaling data travels through message helpers. Device approval must be called only after that native authentication succeeds.

Signaling sequences start at 1, are directional, and are restricted to the JSON exact-integer range (`<= 2^53-1`) by typed wrappers. Opaque message strings are limited to 32 KiB, matching the control server's maximum. Relay modes are `auto`, `never`, and `force`. TURN uses a session or device bearer and remains subject to server relay policy and device approval. Device-token rotation requires an offline broker; the server returns HTTP 409 for an online broker. An offline call invalidates that broker's sessions, so recreate sessions afterward rather than relying on already-revoked tokens in a password-revocation test.
